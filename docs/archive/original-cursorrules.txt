# .cursorrules
# CSCD602 Advanced Software Engineering — 48-Hour Individual Project Examination
# Purpose: Guide Cursor/AI-assisted development toward disciplined software engineering practice,
# not merely rapid feature generation.
#
# IMPORTANT:
# - This project is an INDIVIDUAL examination.
# - The student must understand, verify, and be able to explain all generated code and decisions.
# - Do not fabricate requirements, test results, screenshots, deployment evidence, credentials,
#   repository history, references, metrics, or implementation status.
# - Prefer a small, complete, deployable system over a large unfinished system.

###############################################################################
# 1. PRIMARY PROJECT OBJECTIVE
###############################################################################

You are assisting with a 48-hour Advanced Software Engineering capstone project.

Your goal is to help produce a FUNCTIONAL, DEPLOYABLE software application while explicitly
demonstrating the complete lifecycle:

Requirements
→ Effort Estimation
→ Analysis
→ Design
→ Implementation
→ Testing
→ Technical Debt Management
→ Deployment
→ Documentation
→ Maintenance
→ Future Evolution

Never optimize only for "working code".
Optimize for:
1. correctness,
2. traceability,
3. limited scope,
4. testability,
5. deployability,
6. maintainability,
7. demonstrable software-engineering discipline,
8. viva/demo readiness.

###############################################################################
# 2. EXAM CONSTRAINTS
###############################################################################

Hard constraints:

- Examination duration: 48 hours.
- Work is individual.
- Project must be realistically completable within the available time.
- Application must be functional, not merely:
  - a proposal,
  - requirements document,
  - UI mock-up,
  - static website,
  - non-functional prototype.
- Major prioritised requirements must be implemented.
- Application must be deployed and accessible online.
- Source code must be maintained in a repository.
- External libraries, frameworks, APIs, datasets, and third-party components must be acknowledged.
- The student must be able to explain:
  - requirements,
  - effort estimation,
  - architecture,
  - implementation decisions,
  - testing strategy,
  - technical debt.

When a requested feature threatens the 48-hour scope:
1. flag the scope risk,
2. classify the feature as Must/Should/Could/Won't,
3. recommend the smallest acceptable implementation,
4. record deferred work under Future Evolution or Technical Debt,
5. never silently expand scope.

###############################################################################
# 3. WORKING PRINCIPLES
###############################################################################

Always follow these principles:

- Requirements before implementation.
- Architecture before uncontrolled coding.
- Acceptance criteria before marking a feature complete.
- Tests before claiming correctness.
- Evidence before claiming completion.
- Scope discipline over feature quantity.
- Simple architecture over unnecessary complexity.
- Security by default.
- Traceability from requirement → implementation → test.
- Explicitly record shortcuts caused by the 48-hour constraint.
- Never hide technical debt.
- Never over-engineer.
- Never introduce technologies unless they solve a real project need.
- Never rewrite large working areas without a clear requirement or defect.
- Prefer incremental, reversible changes.
- Preserve deployability throughout development.

###############################################################################
# 5. REQUIREMENTS ENGINEERING RULES
###############################################################################

Before implementing a feature, define or identify its requirement.

Use requirement IDs:

Functional:
- FR-001
- FR-002
- ...

Non-functional:
- NFR-001
- NFR-002
- ...

Business/project constraints:
- CON-001
- CON-002
- ...

Each functional requirement should preferably include:

ID:
Title:
Description:
Actor:
Preconditions:
Trigger:
Main flow:
Alternative/error flow:
Acceptance criteria:
Priority:
Dependencies:
Estimated effort:
Status:

Use unambiguous language:
- "The system shall..."
- "The user shall be able to..."

Avoid vague requirements such as:
- "easy to use",
- "fast",
- "secure",
unless measurable criteria are attached.

Examples:
BAD:
"The system should be fast."

BETTER:
"NFR-003: For normal CRUD operations, the system should return an application response
within 2 seconds under expected examination/demo load."

###############################################################################
# 6. REQUIREMENT PRIORITISATION
###############################################################################

Use MoSCoW unless the project explicitly adopts another method:

MUST:
Essential for the core problem and final demo.

SHOULD:
Important but project remains viable without it.

COULD:
Useful enhancement if time remains.

WON'T FOR THIS VERSION:
Explicitly deferred beyond the 48-hour scope.

Implementation order:
1. Must,
2. Must-path tests,
3. Should,
4. Should-path tests,
5. Could only if sufficient time remains.

Never implement a Could feature while an important Must feature is broken.

###############################################################################
# 7. SCOPE MANAGEMENT
###############################################################################

Maintain explicit scope.

## In Scope
Only features committed for the examination version.

## Out of Scope
Features intentionally excluded from the 48-hour implementation.

## Deferred
Features moved to future evolution due to:
- time,
- dependencies,
- complexity,
- infrastructure,
- testing cost,
- security concerns.

Before adding a new feature, ask internally:
- Is it required?
- Is it a Must?
- What is its estimated effort?
- What existing work may be displaced?
- Will it increase deployment risk?
- Will it create significant technical debt?

If yes, document the decision.

###############################################################################
# 8. SOFTWARE EFFORT ESTIMATION
###############################################################################

Effort estimation is mandatory and must influence scope.

Use ONE justified estimation approach unless the student deliberately compares techniques.

Allowed approaches include:
- Story Points,
- Use Case Points,
- Function Point Analysis,
- COCOMO/COCOMO II,
- Expert Estimation,
- another justified method.

For a small 48-hour application, default to a transparent technique that can be defended,
such as Story Points + person-hour mapping or structured Expert Estimation, unless the project
naturally suits another method.

Maintain an estimation table with fields such as:

ID | Feature/Task | Complexity | Estimate | Person-hours | Priority | Dependency | Notes

Always document:
- why the technique was selected,
- assumptions,
- estimated effort,
- estimated person-hours,
- estimated duration,
- constraints,
- scope impact.

If using story points:
- define the scale,
- define what each point means,
- explain how points map approximately to person-hours,
- do not present story points as precise time measurements.

Example scale:
1 = trivial
2 = small
3 = moderate
5 = complex
8 = high-risk / likely too large for one 48-hour exam project feature

When estimates exceed available capacity:
- reduce scope,
- simplify implementation,
- defer low-priority requirements.

Never manipulate estimates simply to make the plan appear feasible.

# 9. TRACEABILITY

Maintain a lightweight requirements traceability matrix.

Recommended fields:

Requirement ID
→ Design element
→ Implementation module/file
→ Test case ID
→ Status

Example:

FR-003
→ Authentication sequence
→ src/modules/auth/*
→ TC-FR-003-01, TC-FR-003-02
→ PASS

A feature is not "Done" unless:
1. requirement is defined,
2. implementation exists,
3. acceptance criteria are satisfied,
4. relevant test evidence exists,
5. technical debt is recorded where applicable.

# 10. SYSTEM ANALYSIS RULES
###############################################################################

Analyse the problem before selecting technology.

For each major workflow, identify:
- actor,
- input,
- validation,
- business rules,
- data changes,
- output,
- failure conditions,
- permissions,
- external dependencies.

Where relevant, capture:
- current/problem process,
- proposed process,
- use cases,
- system boundary,
- data flow,
- risks,
- constraints.

Never choose architecture only because it is trendy.

###############################################################################
# 11. SYSTEM DESIGN RULES
###############################################################################

Select only diagrams that meaningfully communicate the project.

Possible artefacts:
- system architecture diagram,
- use-case diagram,
- class diagram,
- sequence diagram,
- activity diagram,
- ER/database diagram,
- component diagram,
- UI wireframes,
- data-flow diagram.

Do NOT create every possible diagram.

Recommended minimum for most web applications:
1. system architecture,
2. use-case diagram,
3. ER/database diagram,
4. one sequence/activity diagram for a critical workflow.

Each design artefact must reflect the implemented system.
Do not document a fictional architecture.

###############################################################################
# 12. ARCHITECTURE RULES
###############################################################################

Prefer a small architecture appropriate for 48 hours.

Typical acceptable structure:

Client/UI
→ Application/API
→ Database

Optional only when justified:
→ External service/API
→ Object storage
→ Queue
→ Cache

Avoid unnecessary:
- microservices,
- Kubernetes,
- event-driven infrastructure,
- multiple databases,
- complex CQRS,
- distributed systems,
unless they are central to the problem itself.

Architecture should optimise:
- fast implementation,
- low deployment risk,
- clear separation of concerns,
- testability,
- security,
- maintainability.

Every major architectural decision should have a short rationale.

Maintain an ADR-lite format where useful:

Decision:
Context:
Options considered:
Chosen option:
Reason:
Trade-offs:
Technical debt introduced:

###############################################################################
# 13. TECHNOLOGY SELECTION
###############################################################################

Choose technologies based on:
- student familiarity,
- speed of implementation,
- deployment simplicity,
- library maturity,
- security support,
- testing support,
- project requirements.

Do not change frameworks mid-project without strong justification.

For every significant dependency:
- use a maintained package,
- pin or record versions where practical,
- avoid unnecessary dependencies,
- acknowledge third-party usage in documentation.

Never copy external source code without attribution where attribution is required.

###############################################################################
# 14. CODE ORGANISATION
###############################################################################

Keep code modular but simple.

Typical separation:
- routes/controllers,
- services/use-cases,
- repositories/data access,
- models/entities,
- validation/schemas,
- middleware,
- configuration,
- tests,
- utilities.

Do not create abstractions with only one meaningless implementation merely to appear
"architectural".

Prefer:
- meaningful names,
- small functions,
- single responsibility,
- low duplication,
- clear domain logic,
- explicit errors.

Avoid:
- giant files,
- giant functions,
- magic constants,
- hidden side effects,
- duplicated validation,
- deeply nested conditionals,
- dead code,
- commented-out obsolete code.

###############################################################################
# 15. CODING STANDARDS
###############################################################################

When generating or editing code:

- Follow the project's established style.
- Use descriptive identifiers.
- Keep functions focused.
- Add comments only where intent is not obvious.
- Do not narrate obvious code.
- Validate all untrusted input.
- Handle expected failures explicitly.
- Use environment variables for secrets/configuration.
- Never hard-code passwords, API keys, tokens, or production secrets.
- Never expose stack traces or sensitive internals to end users.
- Avoid silent exception swallowing.
- Log actionable errors without leaking secrets.
- Prefer typed schemas/types where supported.
- Keep business rules out of UI components where practical.
- Use database transactions where multi-step data changes must be atomic.

###############################################################################
# 16. DATABASE RULES
###############################################################################

For database-backed systems:

- design schema before widespread CRUD generation,
- use stable primary keys,
- define foreign keys where appropriate,
- use constraints for essential integrity,
- add indexes only where justified,
- avoid duplicated source-of-truth data,
- use migrations where supported,
- seed only non-sensitive demo data,
- never commit production credentials.

For each main entity document:
- purpose,
- important fields,
- relationships,
- constraints.

Avoid premature database optimisation.

###############################################################################
# 17. API DESIGN RULES
###############################################################################

For APIs:

- use consistent resource naming,
- use correct HTTP methods,
- return meaningful status codes,
- validate request payloads,
- produce consistent error structures,
- enforce authorization server-side,
- never trust client-side role checks,
- version APIs only if necessary.

Typical status expectations:
- 200 success,
- 201 created,
- 204 successful no-content operation,
- 400 malformed/invalid request,
- 401 unauthenticated,
- 403 unauthorized,
- 404 not found,
- 409 conflict,
- 422 validation failure where framework conventions use it,
- 500 unexpected server failure.

Do not expose internal database errors directly.

###############################################################################
# 18. AUTHENTICATION & AUTHORIZATION
###############################################################################

Where authentication is applicable:

- store passwords using a strong password hashing mechanism,
- never store plaintext passwords,
- protect authenticated routes,
- enforce roles/permissions server-side,
- expire or securely manage sessions/tokens,
- implement logout where relevant,
- prevent privilege escalation,
- use secure defaults.

For examination scope, keep authorization simple:
- e.g. User and Admin,
unless additional roles are truly required.

Test:
- valid login,
- invalid login,
- unauthorized access,
- protected resource access,
- logout/session invalidation,
- role restriction.

###############################################################################
# 19. SECURITY RULES
###############################################################################

At minimum review:

- input validation,
- authentication,
- authorization,
- password storage,
- secret management,
- SQL injection,
- XSS,
- CSRF where applicable,
- insecure direct object references,
- unsafe file uploads,
- sensitive-data exposure,
- dependency risks,
- error-message leakage.

Never introduce a known serious security weakness simply to save time.

If a security shortcut is unavoidable:
1. document it as technical debt,
2. identify risk,
3. classify severity,
4. provide mitigation,
5. decide whether deployment remains acceptable.

Critical security debt should be fixed before final deployment whenever feasible.

###############################################################################
# 20. INPUT VALIDATION
###############################################################################

Validate input at the trusted boundary.

Validate:
- required fields,
- types,
- ranges,
- formats,
- enum values,
- identifiers,
- ownership/permission,
- file size/type where uploads exist.

Frontend validation improves UX.
Backend validation is authoritative.

Never rely only on client-side validation.

###############################################################################
# 21. ERROR HANDLING
###############################################################################

Every important workflow must define failure behaviour.

Handle:
- invalid input,
- missing resource,
- duplicate/conflict,
- permission failure,
- database failure,
- external API failure,
- timeout,
- unexpected exception.

User-facing errors should be:
- understandable,
- safe,
- actionable where possible.

Technical logs may contain diagnostic context but never secrets.

###############################################################################
# 22. TECHNICAL DEBT MANAGEMENT
###############################################################################

Technical debt is a required examination component.

Maintain:
docs/technical-debt-register.md
or an equivalent section/file.

Each significant debt item MUST use:

Debt ID:
Debt:
Cause:
Impact:
Priority:
Category:
Status:
Proposed Resolution:
Target Version/Time:
Related Requirement/Module:

Required conceptual chain:
Debt → Cause → Impact → Priority → Proposed Resolution

Suggested categories:
- architecture,
- code quality,
- testing,
- security,
- performance,
- documentation,
- dependency,
- deployment,
- UX,
- data.

Suggested priorities:
- Critical,
- High,
- Medium,
- Low.

Status classes:
- Acceptable temporarily,
- Scheduled for future resolution,
- Critical/immediate.

Examples of legitimate exam-related debt:
- simplified role model,
- limited automated test coverage,
- temporary local file storage,
- missing rate limiting,
- duplicated code,
- incomplete refactoring,
- limited observability,
- minimal performance testing,
- manual deployment step,
- dependency upgrade deferred.

Do not invent debt just to fill documentation.
Record actual trade-offs.

Whenever Cursor proposes a shortcut, it should ask internally:
"Does this introduce technical debt?"
If yes, add/update the debt register.

Critical debt should not be deferred without explicit justification.

###############################################################################
# 25. AUTOMATED TEST RULES
###############################################################################

Write automated tests for logic with high defect risk.

Prioritise tests for:
- authentication,
- authorization,
- business rules,
- calculations,
- validation,
- service methods,
- critical APIs,
- important persistence logic.

Avoid spending excessive examination time testing trivial framework behaviour.

When fixing a defect:
1. reproduce it,
2. add/update a test where practical,
3. fix the defect,
4. rerun related tests,
5. record the defect if relevant to the testing report.

Expected outcome: ...
Actual outcome: ...
Status: PASS

UAT should demonstrate that implemented Must requirements solve the intended problem.

###############################################################################
# 27. DEFECT MANAGEMENT
###############################################################################

Maintain a lightweight defect log.

Fields:

Description
Severity
Related requirement
Detected during
Root cause
Fix
Status
Retest result

Severity:
- Critical: blocks core use/deployment/security
- High: major requirement broken
- Medium: workaround exists
- Low: cosmetic/minor

Fix Critical and High defects before optional enhancements.

###############################################################################
# 28. DEFINITION OF DONE
###############################################################################

A requirement is DONE only if:

- implementation is complete,
- code builds/runs,
- acceptance criteria are met,
- validation exists,
- failure cases are handled,
- relevant tests have been executed,
- technical debt is documented,
- documentation is updated where needed,
- feature works in the deployed environment if deployment affects it.

"Code generated" is NOT equal to "Done".

###############################################################################
# 29. DEPLOYMENT RULES
###############################################################################

The final application must be accessible online.

Potential platforms include:
- Vercel,
- Netlify,
- Render,
- suitable cloud platform,
- another appropriate host.

Choose the deployment approach that minimises examination risk.

Before finalising deployment verify:
- production build succeeds,
- environment variables are configured,
- database connection works,
- migrations are applied,
- API endpoints work,
- authentication works,
- static assets load,
- critical workflows work,
- no secrets are exposed,
- URLs are stable,
- test credentials work.

Never mark deployment complete based only on a successful build.
Test the LIVE application.

###############################################################################
# 30. DEPLOYMENT CONFIGURATION
###############################################################################

Keep production configuration separate from development.

Use:
- environment variables,
- .env.example,
- documented variable names.

Never commit:
- .env,
- API secrets,
- database passwords,
- private keys,
- admin passwords.

Provide `.env.example` with placeholders only.

- unexpected exceptions,

Do not log:
- passwords,
- access tokens,
- secret keys,
- full sensitive records.

Avoid building complex monitoring infrastructure unless required.

# 61. PROJECT-SPECIFIC OVERRIDE — LEGALCONNECT GHANA
###############################################################################

Project working title:
LegalConnect Ghana — An AI-Powered Platform for Improving Access to Legal Services

Project domain:
Legal-service access, legal-intake support, lawyer/law-firm discovery, consultation requests,
and AI-assisted triage for users in Ghana.

Core problem framing:
The project does NOT assume that Ghana lacks lawyers or law firms. The software problem is the
fragmented and sometimes difficult process ordinary users may face when trying to identify the
appropriate type of legal professional, understand where to start, describe their issue clearly,
and connect with a suitable legal service provider.

The system should therefore reduce ACCESS FRICTION between:
- individuals seeking legal assistance, and
- lawyers/law firms offering relevant services.

The application is an ACCESS, TRIAGE, MATCHING, and COORDINATION platform.
It is NOT a replacement for a lawyer and must NOT present itself as providing professional legal
advice.

###############################################################################
# 62. PROJECT VALUE PROPOSITION
###############################################################################

The platform should help a user move from:

"I have a legal problem but I do not know where to start"

into a structured flow:

Describe legal concern
→ AI-assisted triage
→ legal category suggested
→ structured case summary generated
→ relevant professionals identified
→ user reviews suitable lawyer/law-firm profiles
→ consultation request submitted
→ lawyer reviews intake and responds outside/inside the supported workflow

The AI component exists to improve access and reduce intake friction.
Do NOT add AI merely as a chatbot decoration.

###############################################################################
# 67. AI FEATURE 1 — LEGAL ISSUE TRIAGE
###############################################################################

Purpose:
Help transform an unstructured user description into structured intake data.

Input should include only data necessary for triage, for example:
- user's free-text concern,
- optional location,
- optional urgency indicators explicitly provided by the user.

Expected AI output MUST be structured and validated against a schema similar to:

{
  "category": "Employment Law",
  "summary": "Concise neutral summary of the user's stated issue.",
  "urgency": "NORMAL | IMPORTANT | URGENT",
  "keywords": ["salary", "termination"],
  "confidence": 0.82,
  "needsHumanReview": false
}

The exact categories MUST come from the application's configured legal-category list.
The model must not invent uncontrolled categories when a category list is supplied.

If confidence is low or classification is ambiguous:
- do not pretend certainty,
- mark for human/user confirmation,
- offer top plausible categories if the implementation supports it.

###############################################################################
# 68. AI FEATURE 2 — INTAKE SUMMARISATION
###############################################################################

The AI summary should:
- preserve the user's meaning,
- use neutral language,
- separate facts stated by the user from assumptions,
- avoid determining legal liability,
- avoid declaring that a law was violated,
- avoid predicting court outcomes,
- avoid inventing dates, evidence, people, documents, or events.

Recommended structured intake fields:

- originalDescription
- category
- conciseSummary
- keyFacts[]
- requestedHelp (if inferable with reasonable confidence)
- urgency
- confidence
- needsHumanReview

The ORIGINAL user text should remain stored where project privacy rules allow so the lawyer can
compare the AI summary with the user's own words.

Never overwrite the original intake with only an AI-generated summary.

###############################################################################
# 69. AI FEATURE 3 — LAWYER MATCHING
###############################################################################

For the examination version, lawyer matching should remain SIMPLE, EXPLAINABLE, and TESTABLE.

Recommended matching inputs:
- classified legal category,
- lawyer practice areas,
- lawyer status/approval,
- optional city/region,
- optional availability,
- optional language only if collected.

Prefer deterministic ranking over opaque AI ranking.

Example scoring concept:
- practice-area exact match: highest weight,
- location match: secondary weight,
- availability: secondary weight,
- verified/active status: mandatory eligibility condition.

AI may help classify the issue, but the final lawyer filtering/ranking should normally be
implemented in application logic so it can be tested and explained during the viva.

Every recommendation shown to the user should be explainable, e.g.:
"Recommended because this lawyer lists Employment Law as a practice area and is available in
your selected region."

Do not claim a lawyer is "the best" unless the system has an objective and defensible basis.

# 71. LEGAL-SAFETY BOUNDARY
###############################################################################

- intake summarisation,
- general orientation,

NOT TO BE PRESENTED AS AI AUTHORITY:

###############################################################################
# 72. AI PROMPTING RULES
###############################################################################

All legal-triage prompts must:
- define the model's limited task,
- provide the allowed category list,
- prohibit legal conclusions,
- prohibit fabrication,
- request structured output,
- instruct the model to flag ambiguity,
- instruct the model to use only information supplied by the user for factual summaries.

Prompt template principles:

ROLE:
You are an intake-classification assistant for a legal-service access platform.

TASK:
Classify and structure the user's issue for routing to a legal professional.

DO:
- summarise neutrally,
- select only from allowed categories,
- extract explicitly stated facts,
- identify ambiguity,
- return JSON.

DO NOT:
- provide a legal conclusion,
- determine whether a crime/tort/breach definitely occurred,
- invent facts,
- guarantee outcomes,
- impersonate a lawyer.

Never trust model output without schema validation.

###############################################################################
# 73. AI OUTPUT VALIDATION
###############################################################################

Every AI response used by application logic must be validated.

Validate:
- JSON syntax,
- required fields,
- category membership,
- urgency enum,
- confidence range,
- array/string lengths,
- null/optional values.

If validation fails:
1. retry only if retry behaviour is deliberately implemented,

Example fallback:
- category = "Other / Needs Review"

# 82. PROJECT-SPECIFIC FUNCTIONAL REQUIREMENTS BASELINE
###############################################################################

Use these as a STARTING BASELINE only. Refine them in the actual SRS.

FR-001 — Account Registration
The system shall allow a citizen to create an account using the required registration fields.

FR-002 — Authentication
The system shall authenticate registered users and establish an authorised session.

FR-003 — Lawyer Profile Management
The system shall maintain lawyer/legal-service-provider profiles including configured practice
areas and availability/profile status.

FR-004 — Legal Concern Submission
The system shall allow a citizen to submit a free-text description of a legal concern.

FR-005 — AI Legal Issue Classification
The system shall analyse a submitted legal concern and suggest one configured legal category,

FR-006 — AI Intake Summary

The system shall allow users to view/search/filter eligible lawyer profiles.

FR-009 — Consultation Request
The system shall allow a citizen to send a consultation request to a selected eligible lawyer.

FR-010 — Consultation Management
The system shall allow authorised users to view and update consultation-request status according
to their role.

FR-011 — Administration
The system shall allow an administrator to manage relevant users, lawyer profiles, and legal
categories within the MVP scope.

FR-012 — AI Failure Fallback
The system shall preserve the user's submitted concern and provide a recoverable workflow when
the AI service cannot produce a valid result.

Do not treat these IDs as final until the requirements document is reviewed.

###############################################################################
# 83. PROJECT-SPECIFIC NON-FUNCTIONAL REQUIREMENTS BASELINE
###############################################################################

NFR-001 — Security
The system shall protect authenticated and role-restricted operations through server-side access
control.

NFR-002 — Privacy
The system shall minimise collection/exposure of legal-intake information and shall not expose
one user's private intake to unauthorised users.

NFR-003 — Reliability
Failure of the AI provider shall not cause loss of a user's submitted legal concern.

NFR-004 — Usability
A first-time user should be able to describe a concern and reach a relevant lawyer-discovery or
consultation step without requiring knowledge of legal terminology.

NFR-005 — Maintainability
AI-provider-specific logic shall be encapsulated behind a dedicated service/adapter boundary.

NFR-006 — Performance
Define a realistic response target for ordinary application operations and separately document
AI-dependent latency based on actual observed behaviour.

NFR-007 — Explainability
Lawyer recommendations shall be explainable using visible matching criteria rather than an
unverifiable AI claim.

NFR-008 — Availability
The deployed application shall remain accessible for examination/demo grading subject to the
selected hosting platform's limitations.

###############################################################################
# 84. ACCEPTANCE CRITERIA EXAMPLES
###############################################################################

FR-005 acceptance criteria example:
- Given a non-empty legal concern,
- when the AI triage service returns a valid supported category,
- the system stores/displays that category with the intake,
- and preserves the original user description.

Fallback:
- Given an AI timeout or invalid output,
- the system preserves the intake,
- marks the item for review/fallback,
- and shows a controlled message rather than a server error.

FR-008 acceptance criteria example:
- only active/eligible lawyer profiles are returned,
- at least one matching practice area must exist for category-based recommendations,
- the user can see why a lawyer was recommended.

###############################################################################
# 85. UX RULES FOR ORDINARY USERS
###############################################################################

The interface must not assume users understand legal terminology.

Prefer:
"Tell us what happened"
over:
"Select the applicable jurisprudential cause of action"

Prefer plain-language category descriptions.

The intake screen should make clear:
- users can describe the issue in their own words,
- AI will organise the request,
- a legal professional remains responsible for professional advice.

Avoid intimidating forms with dozens of fields.
Start with a small number of fields and progressively request more only if required.

# 87. AI TECHNICAL DEBT ITEMS TO WATCH
###############################################################################

Likely technical debt candidates include:
- relying on a general-purpose LLM rather than a domain-specific classifier,
- limited labelled evaluation dataset,
- prompt-based categorisation rather than trained model,
- limited explainability beyond category/match criteria,
- no human moderation dashboard for ambiguous classifications,
- hard-coded initial category taxonomy,
- provider dependency,
- no advanced prompt-injection defenses,
- limited AI observability,
- no provider failover,
- no RAG knowledge base.

Only record items that actually apply.

Do not treat all of these as defects.
Some are acceptable temporary debt for a 48-hour MVP if risk is controlled and documented.
